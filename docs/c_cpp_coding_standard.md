本書は、`jp.co.entersystem.jninative`のWindows DLL、JNI、Windowsドライバ、
コンソールアプリケーションの現行ソース、およびJavaコーディング規約を基準として、
他プロジェクトでも同じ品質のコメントとコードを再現できるように規約を定義する。

現行ソースには、長期保守、旧Microsoftコンパイラ、Windows DDK、生成コード、
第三者コードに由来する表記揺れがある。本書ではそれらをそのまま規約化せず、
次の優先順位で正規形を定める。

1. 対象プロジェクトの`AGENTS.md`、ビルド要件、安全要件
2. 本書の規則
3. 変更対象ファイル周辺の既存形式
4. 使用する言語規格とプラットフォームの公式規則

この優先順位は、言語・ABIの制約や第三者の許諾条件を上書きするものではない。
DriverCrateはC++20／Windows x64／UTF-8 BOMなし／LFを採用し、namespaceは`drivercrate`とする。
JNI、カーネルドライバ、他architecture、基準プロジェクトのCP932／CRLFは、対応箇所の参考に限る。
今回の明示的な全source移行には第3.4節の通常の最小変更範囲ではなくADR 0141の対象集合を適用する。

本書では、次の用語を使用する。

- 「必須」: 新規コードおよび変更コードで必ず守る。
- 「推奨」: 特別な理由がない限り守る。
- 「既存踏襲」: 変更対象外を一括整形せず、周辺ソースに合わせる。
- 「公開API」: 他の翻訳単位、DLL、Java、ドライバ、外部製品から呼び出される境界。
- 「所有する」: 解放、クローズ、参照解除などの後始末責任を持つこと。

## 2. 適用範囲と適用除外

### 2.1 適用範囲

本書は、原則として次のファイルへ適用する。

- Cソースおよびヘッダ: `.c`、`.h`
- C++ソースおよびヘッダ: `.cc`、`.cpp`、`.cxx`、`.hh`、`.hpp`、`.hxx`
- JNIネイティブ実装
- WindowsユーザーモードDLLおよび実行ファイル
- Windowsカーネルモードドライバ
- C/C++のテストコード

### 2.2 適用除外

次のファイルは、原則として内容を直接変更せず、生成元または提供元の規則に従う。

- `javac -h`等によって生成されるJNIヘッダ
- Windows SDK、WDKその他のツールが生成するファイル
- 外部ライブラリおよび第三者コード
- ライセンス条件により書式変更が制限されるコード
- ビルド生成物、解析結果、変換済み中間ファイル

適用除外ファイルへ自社都合の修正が必要な場合は、原本との差分、修正理由、
再生成時の反映方法を別文書またはパッチとして管理する。第三者の著作権表示や
ライセンス文は変更しない。

## 3. 最重要原則

DriverCrateの`.clang-format`では`ReflowComments: false`を指定する。
コードの整形時にfile headerや関数契約のDoxygen項目を連結せず、
項目構造を維持するためである。行長は100文字を目安、120文字以内を推奨し、
literal・URL等の分割できない内容を保持する。コメントの折返しは変更時に確認する。
DriverCrateでは右端の装飾枠と関数署名の手書き複製を廃止している。

### 3.1 制作者名

新規作成・変更の制作者名は、常に次の表記で統一する。

```text
Shunji Ogawa
```

次の箇所では、大文字・小文字、空白を含めて完全一致させる。

- ファイルヘッダの`@author`
- ファイルヘッダ内の更新履歴の`author`列
- 製品更新履歴の`Author`列
- 文書や設計書に制作者を記録する場合

`ogawa`、`尾川 俊司`、誤記を新しい履歴へ追加しない。ただし、既存履歴、
第三者コード、生成コードの著作者表示は改変しない。

### 3.2 コメントの目的

コメントは、コードを日本語へ置き換えるためではなく、次の情報を残すために記述する。

- その処理が必要な業務上、制御上、安全上の理由
- 条件成立時に保証すること、抑止すること、失敗時の動作
- 状態遷移の開始状態、終了状態、復帰条件
- API、プロトコル、IOCTL、bit、単位、タイムアウトなどの外部仕様
- ポインタのNULL可否、バッファ長、文字列終端、所有権、寿命
- リソースを取得・解放する主体と、異常経路での後始末
- スレッド、割り込み、コールバック、排他、IRQLなどの実行条件
- JNI参照、Java例外、配列要素の取得・解放に関する契約
- 一見不要に見える処理や互換処理を残す理由

次のような、コードを読めば分かるだけのコメントは避ける。

```cpp
// countを1増やす
count++ ;
```

処理の目的または成立条件を記述する。

```cpp
// 次回の再送上限判定へ進めるため送信回数を更新する
count++ ;
```

### 3.3 コメントとコードの同時更新

コードを変更した場合は、関係するファイルヘッダ、関数コメント、処理コメント、
公開ヘッダ、設計上の制約も同じ変更として更新する。コメントと実装が矛盾する場合、
コメントが多いことは品質とはみなさない。

### 3.4 変更範囲

既存ファイルを変更する場合は、要求を満たす最小範囲だけを変更する。
規約違反を発見しても、今回の変更対象でない箇所を一括整形しない。

新規コードは本書の正規形で作成する。既存コードを変更する場合は、公開ABI、
ファイルの文字コード、改行形式、対象コンパイラ、周辺形式を確認してから変更する。

## 4. 言語規格、文字コード、改行

### 4.1 言語規格

プロジェクトは、使用するC/C++言語規格とコンパイラをビルド設定へ明記する。
新規プロジェクトでは、ツールチェーンが対応する範囲でC11以上、C++17以上を推奨する。
古いSDK、WDK、組み込み処理系を使用する場合は、採用できない構文と代替規則を
プロジェクト固有規約へ記載する。

CファイルはCとして、C++ファイルはC++として記述する。C++でCのAPIを公開する場合は、
必要な範囲だけ`extern "C"`を使用する。

### 4.2 文字コードと改行形式

新規プロジェクトでは、原則としてUTF-8（BOMなし）を使用し、コンパイラの
ソース文字セットもUTF-8へ固定する。改行形式は`.editorconfig`等でプロジェクト単位に
統一する。指定がない場合はLFを標準とする。

基準プロジェクトの既存C/C++ソースは、主にCP932およびCRLFである。
既存ファイルの一部だけを変更する作業では、文字化けと不要な全行差分を防ぐため、
CP932、BOM有無、CRLFを維持する。文字コードの一括変換は独立した移行作業として行う。

### 4.3 言語と表記

- コメントおよび更新履歴は日本語で記述する。
- 識別子は英語で記述する。
- API名、規格名、エラー名などの正式名称は原文を使用してよい。
- 短い処理コメントでは末尾の`。`を省略し、Doxygenの説明文では`。`を付ける。
- 同じ意味に「解放」と「開放」などを混在させず、原則としてリソースには「解放」を使う。

## 5. ソースファイルの基本構成

### 5.1 実装ファイル

C/C++実装ファイルは、原則として次の順序で構成する。

1. ファイルヘッダコメント
2. 対応する自プロジェクトヘッダ
3. C/C++標準ライブラリヘッダ
4. OS、SDK、外部ライブラリヘッダ
5. その他の自プロジェクトヘッダ
6. ファイル内定数、型、静的変数
7. 内部関数の前方宣言
8. 公開関数
9. 内部関数

対応するヘッダを最初にインクルードし、そのヘッダが単独で成立することを確認する。
ただし、Windowsヘッダの順序制約などがある場合は、理由をコメントして必要な順序を優先する。

```cpp
#include "device_controller.h"

#include <cstdint>
#include <string>

#include <windows.h>

#include "driver_install.h"
```

### 5.2 ヘッダファイル

ヘッダファイルは、原則として次の順序で構成する。

1. ファイルヘッダコメント
2. インクルードガードまたは`#pragma once`
3. 必要最小限の`#include`
4. 定数、列挙型、型宣言
5. 公開関数またはクラス宣言
6. インクルードガード終端

新規の移植可能なヘッダではインクルードガードを標準とする。

```c
#ifndef EXAMPLE_DEVICE_CONTROLLER_H
#define EXAMPLE_DEVICE_CONTROLLER_H

/* 宣言 */

#endif  // EXAMPLE_DEVICE_CONTROLLER_H
```

`#include`で足りる依存関係を、偶然のインクルード順序に依存させない。
C++ヘッダでは、完全型が不要な場合に前方宣言を検討する。

### 5.3 セクションコメント

長いファイルでは、基準プロジェクトの形式を引き継ぎ、意味のある区分だけを記載する。

```cpp
//------------------------------------------------------------------------------
// 定数定義
//------------------------------------------------------------------------------

//------------------------------------------------------------------------------
// 内部型定義
//------------------------------------------------------------------------------

//------------------------------------------------------------------------------
// 内部関数定義
//------------------------------------------------------------------------------
```

空のセクションは残さない。装飾線は半角ハイフンで統一し、全角空白やタブで
枠幅を調整しない。

## 6. 命名規則

### 6.1 基本命名

| 対象 | 形式 | 例 |
|---|---|---|
| C/C++ソースファイル | lower_snake_case | `driver_install.cpp` |
| C/C++ヘッダファイル | lower_snake_case | `driver_install.h` |
| C++クラス、構造体、共用体、型別名 | UpperCamelCase | `DeviceController`、`ScanInfo` |
| C/C++関数、C++メソッド | lowerCamelCase | `loadDeviceDriver` |
| ローカル変数、引数、構造体メンバー | lowerCamelCase | `driverHandle` |
| C++のprivateメンバー | lowerCamelCaseの末尾に`_` | `driverHandle_` |
| 定数、列挙値、マクロ | UPPER_SNAKE_CASE | `SCAN_CYCLE_MIN_US` |
| 名前空間 | lower_snake_case | `device_control` |
| boolean取得 | `is`、`has`、`can`、`should` | `isRunning` |
| インクルードガード | プロジェクト名を含むUPPER_SNAKE_CASE | `JCSIM_DEVICE_H` |

公開済みAPI、JNI関数名、Windowsが要求する`DriverEntry`、`DllMain`等は例外とし、
定められた名前を変更しない。既存の`LoadDeviceDriver`等も、互換性のため一括改名しない。

### 6.2 名称の内容

名称は、型や一時的な実装方法ではなく役割を表す。新規コードでは、
`data1`、`wk`、`tmp2`、`flg`のように意味を特定できない名称を避ける。

ポインタや型を示すハンガリアン記法（`pName`、`dwSize`、`bFlag`等）は、
既存APIとの整合が必要な場合を除き、新規コードへ導入しない。代わりに
`driverName`、`bufferSize`、`isInitialized`のように役割を表す。

### 6.3 単位、サイズ、個数

時間、容量、アドレス、個数は名称またはコメントから単位を判断できるようにする。

```cpp
constexpr std::uint32_t RETRY_TIMEOUT_MS = 3'000U ;
std::size_t bufferSizeBytes ;
std::uint32_t scanCycleUs ;
```

`size`が、要素数、バイト数、バッファ容量、使用済み長のどれを表すか明記する。
物理アドレス、仮想アドレス、ユーザーアドレスなど、アドレス空間が異なる値は
名称で区別する。

### 6.4 対になる名称

開始と終了、取得と解放、登録と解除などは、対になることが分かる名称を使用する。

- `start` / `stop`
- `initialize` / `finalize`
- `open` / `close`
- `acquire` / `release`
- `registerCallback` / `unregisterCallback`

## 7. インデント、空白、波かっこ

### 7.1 インデント

基準プロジェクトとの整合のため、インデントにはタブを使用する。タブ幅は4とする。
行末空白は残さない。連続する変数、定数、構造体メンバーでは、型、識別子、
初期値、行末コメントの開始位置を、同じ論理グループ内でタブによりそろえる。

```cpp
HANDLE			driverHandle		= INVALID_HANDLE_VALUE ;	// ドライバハンドル
std::size_t		bufferSizeBytes		= 0U ;						// バッファ容量（byte）
bool			isInitialized		= false ;					// 初期化完了区分
```

整列は同じ役割を持つ連続した宣言の範囲だけで行い、離れた宣言へ合わせるために
過剰な空白を入れない。行末コメントが長くなる場合は、無理に右側へ配置せず、
宣言直前のコメントへ移す。

自動フォーマッタを使用する場合は、プロジェクトで同一設定を共有し、変更対象外へ
無差別に適用しない。

DriverCrateでは前置`///`とフィールド宣言を一体として扱う。同じ型・access区分内の
連続するdata memberは、個別の`///`や一空行を挟んでも同じ論理groupで整列する。
method、型宣言、access label、preprocessor、明示sectionを越えて整列しない。
複雑な複数行宣言は独立して整形し、コメントを別の要素へ移さない。

### 7.2 丸かっこ、演算子、セミコロン

基準プロジェクトの形式に合わせ、制御構文と関数呼び出しでは開始丸かっこの内側へ
1スペース入れる。引数なしの場合は空白を入れない。

```cpp
if( isReady) {
	process( target, count) ;
}

initialize() ;
```

この片側空白は関数宣言の引数にも適用するが、算術・比較のグループ括弧には適用しない。
例えば`value > (MAX_VALUE - digit) / RADIX`のグループ内側には空白を置かない。
`>`や`>>`だけを根拠にtemplate呼出しと判定してはならない。

二項演算子の前後へ1スペースを入れる。実行文、宣言文、`return`文では、
セミコロン前へ1スペースを入れる。`#include`、プリプロセッサ式、
`for`ヘッダ内の区切りは、その構文の標準的な可読性を優先する。

ポインタと参照の`*`、`&`は識別子側へ付ける。1つの宣言文では1変数だけを宣言する。

```cpp
const char *driverName ;
Device &device = devices.front() ;
```

### 7.3 波かっこ

関数定義の開始波かっこは次の行へ置く。制御文、クラス、構造体、名前空間の
開始波かっこは宣言と同じ行へ置く。

```cpp
bool startDevice( Device *device)
{
	// デバイス情報が不完全な場合は開始しない
	if( device == nullptr) {
		return false ;
	}

	return true ;
}
```

1文だけの`if`、`for`、`while`でも波かっこを省略しない。

### 7.4 空行

意味のまとまりごとに1行空ける。`if`、`for`、`while`等の閉じかっこ後は、
次の独立した処理まで1行空ける。ただし、次の連続構造では空けない。

- `if`と`else`
- `try`と`catch`
- `catch`と次の`catch`または`finally`相当の後始末
- `do`と`while`

### 7.5 行長と継続行

1行は120文字以内を推奨する。生成されたJNI宣言、URL、分割できない文字列等は
例外とする。長い条件や引数は論理単位で改行し、継続行をそろえる。

```cpp
if(( currentState == State::WAITING_REPLY) &&
   (elapsedTimeMs >= responseTimeoutMs)) {
	// 応答待ちが期限を超えたため再送予約へ戻す
	state = State::SEND_PENDING ;
}
```

## 8. コメント規約

### 8.1 コメント形式の使い分け

| 用途 | 形式 |
|---|---|
| ファイル、関数、メソッド、名前付き型の契約 | Doxygen形式の`/** ... */` |
| 構造体・共用体・クラスのフィールド、列挙値 | 宣言直前のDoxygen形式`/// ...` |
| ローカル変数、グローバル変数、ファイルスコープ変数、定数 | `// ...` |
| 処理ブロック、条件、状態遷移 | 独立行の`// ...` |
| 複数行を縦に比較する補足 | 行末の`// ...` |
| 第三者ライセンス | 原文の形式を維持 |

Java規約と同様に、複数行が1つの契約として関連するファイル、型、関数、メソッドの
コメントは`/** ... */`を使用する。関数とメソッドは、引数がない場合や説明が短い場合でも、
将来の契約追加と形式統一のため同じ形式を維持する。

構造体・共用体・クラスのフィールドと列挙値は、公開・非公開を問わず、宣言直前の
`/// ...`で個別に文書化する。複数行になる場合は各行を`///`で開始し、空行を挟まず
対象宣言へ続ける。通常の`//`はDoxygenのbrief／detailed descriptionにならないため、
これらの要素には使用しない。行末の`///< ...`も使用せず、前置形式へ統一する。

ローカル変数、グローバル変数、ファイルスコープ変数、定数、処理説明は、Doxygenの
要素別文書へ出力する対象ではないため`// ...`を使用する。同じ要素へ`///`と
`/** ... */`を重複して付けない。

class内のstatic／constexpr定数はdata memberの規則を優先して`///`とする。
local classのフィールドも対象とし、関数引数は関数の`@param`で説明する。
名前付き型の説明には、短くても`/** ... */`を使用する。

```cpp
 * <pre>
 * VerNo.         author        update     comment
 * Ver.01.00.00   Shunji Ogawa  2026/09/02 新規作成
 * </pre>
 *
 * @note 本ファイルはデバイスハンドルの所有権を管理します。
 */
//------------------------------------------------------------------------------
```

ヘッダの`@brief`には、単なる「関数定義」ではなく、そのファイルが提供する責務を
記載する。実装ファイルと対応ヘッダで説明を重複させる場合は、公開契約をヘッダへ、
実装上の制約を実装ファイルへ記載する。

DriverCrateの自作file headerは、`@author`直後へ`@copyright`を一件記載する。
その後の独立した`@par ライセンス`へ、SPDX識別子、Apache-2.0の適用説明、
ルートLICENSEの案内、Apache公式URLを順に一件ずつ記載する。
タグなしCopyright行、`All Rights Reserved.`、MITライセンス節は併記しない。
他プロジェクトへの適用時は、そのプロジェクトの権利者・年・許諾条件を別途確認する。

```text
 * @author Shunji Ogawa
 * @copyright Copyright (c) 2026 EnterSystem CO.,LTD.
 *
 * @par ライセンス
 * SPDX-License-Identifier: Apache-2.0
 * 本ファイルには Apache License, Version 2.0 が適用されます。
 * ライセンス全文はプロジェクトルートの LICENSE を参照してください。
 * https://www.apache.org/licenses/LICENSE-2.0
```

ルートのLICENSEにはApache License, Version 2.0の公式英語全文を保存する。
年は利用者指定の2026とし、fileの作成日・更新履歴を変更する根拠にしない。
`@see LICENSE`は追加してよいが、ライセンス節の案内の代替にはしない。
このheaderは利用者がCPP見本一件で手動確定し、G12-X4e-02lでchecker追従と
全355自作sourceへの適用を完了した。
第三者の許諾・原著作権表示はこの形式へ一括置換しない。

### 8.3 更新履歴と版数

`@version`は`01.00.00`のように、2桁ずつの3要素をピリオドで区切り、`Ver.`を付けずに
記載する。更新履歴の版数は`Ver.01.00.00`のように、同じ3要素の先頭へ`Ver.`を付ける。

ファイルを変更した場合は変更区分に応じて版数を上げ、更新履歴を末尾へ一行追加する。
同じ版数を複数の更新履歴へ再利用せず、新しい版数は直前の版数より大きくする。
過去行は変更せず、最新更新履歴の`Ver.`を除いた版数と`@version`を一致させる。

| 変更 | 版数例 |
|---|---|
| 新規作成 | `01.00.00` |
| 機能・仕様追加 | `01.01.00` |
| 小規模修正・不具合修正 | `01.00.01` |
| 大規模な非互換変更 | 第1要素を更新。個別判断とする |

日付は`YYYY/MM/DD`形式とし、commentには変更対象と結果を特定できる内容を書く。

```text
Ver.01.00.01   Shunji Ogawa  2026/09/03 応答タイムアウト時にハンドルを解放しない不具合修正
```

「修正」「対応」のみの履歴は記載しない。バージョン管理システムのログだけに依存せず、
リリース時に必要なファイル単位の履歴を残す。

DriverCrateの製品版はCMakeの`project(VERSION)`、本節は独立したファイル版である。
コメント・書式だけの変更も小規模修正として第3要素を上げるが、一つの論理変更の編集中に
保存・整形・testを繰り返すたびには採番しない。新しい機能追加時は第3要素を00へ戻す。
各要素は00～99、99を超える場合は直上へ繰り上げて下位を00へ戻す。
`99.99.99`の次は自動採番せず規約の変更を判断する。

旧製品版`Ver.0.1.0`等の履歴は、file header内の
`@par 移行前更新履歴（製品版）`の`<pre>`へ、内容・順序を保持して移す。
旧行を新しいfile版の連番へ改変せず、`@par 更新履歴`に`Ver.01.00.00`で
独立版への移行理由を記載する。作成日は維持し、既に新形式のfileは現版を引き継ぐ。
移行前節に新変更を追記しない。厳密な移行・検査条件はADR 0141第3節へ従う。

### 8.4 関数・メソッドコメントの適用範囲

公開・非公開、`static`、コンストラクタ、デストラクタを問わず、すべての自作関数と
メソッドへDoxygenコメントを付与する。短いgetter、setterでも、対象、単位、
スレッド安全性など名称だけでは分からない契約を記載する。

オーバーライドで基底クラスの契約と完全に同じ場合は`@copydoc`等を使用してよい。
追加の前提、後処理、例外がある場合は明記する。

公開関数の説明は宣言側のヘッダを正とし、実装側へ同じ説明を複製しない。
内部関数は実装ファイルの定義直前へ記載する。

### 8.5 関数・メソッドコメントの基本形式

```cpp
//------------------------------------------------------------------------------
/**
 * @brief デバイスドライバをロードします。
 *
 * 既存サービスを停止・削除した後、指定ファイルをサービスとして登録し、
 * 呼び出し元が使用するデバイスハンドルを取得します。
 *
 * @param[in] driverName ドライバ名称。NULL不可、NULL終端文字列。
 * @param[in] driverPath ドライバファイルの絶対パス。NULL不可、NULL終端文字列。
 * @param[out] deviceHandle 取得したハンドルの格納先。NULL不可。
 *                          成功時は呼び出し元がCloseHandleで解放します。
 * @return 処理結果。
 * @retval true ロードおよびハンドル取得に成功。
 * @retval false ロードまたはハンドル取得に失敗。
 * @pre 管理者権限で実行されていること。
 * @post 失敗時、deviceHandleの参照先はINVALID_HANDLE_VALUEです。
 */
//------------------------------------------------------------------------------
bool loadDeviceDriver( const char *driverName,
                       const char *driverPath,
                       HANDLE *deviceHandle) ;
```

タグは必要なものだけを、原則として次の順序で記載する。

1. `@brief`
2. 詳細説明
3. `@tparam`
4. `@param[in]`、`@param[out]`、`@param[in,out]`
5. `@return`、`@retval`
6. `@throws`（C++）
7. `@pre`
8. `@post`
9. `@note`
10. `@warning`
11. `@see`

宣言を変更した時は、引数の順序と`@param`の順序を一致させる。

### 8.6 引数の記載内容

ポインタ、配列、ハンドル、文字列には、該当する次の情報を記載する。

- 入力、出力、入出力の区分
- NULL可否。NULL可の場合の意味
- 配列の要素数、バッファの容量、読み書きする長さとその単位
- NULL終端の要否、文字コード
- 所有権を移譲するか、借用するだけか
- 参照先が有効でなければならない期間
- 呼び出し元が必要とする初期値
- 成功時と失敗時に出力値がどうなるか
- エイリアスを許可するか

```c
/**
 * @brief 受信データを解析します。
 *
 * @param[in] data 読み取り専用データ。NULL不可。
 * @param[in] dataSizeBytes dataが指す有効データ長（byte）。1以上。
 * @param[out] result 解析結果の格納先。NULL不可。
 *                    失敗時はRESULT_INVALIDに設定します。
 * @return 解析に成功した場合はtrue、失敗した場合はfalse。
 */
bool parseData( const uint8_t *data,
                size_t dataSizeBytes,
                ParseResult *result) ;
```

ポインタ引数には、可能な限り`const`を付け、コメントと型の両方で読み取り専用を示す。

### 8.7 戻り値、エラー、例外

非`void`関数には`@return`を記載する。複数の戻り値やステータスを返す場合は
`@retval`ですべての意味を列挙する。`BOOL`、`bool`、`jboolean`では、
成功・失敗、該当・非該当のどちらを表すか明記する。

エラーコードでは、値だけでなく次を記載する。

- どの分類の失敗か
- OSエラーや`GetLastError()`を維持するか
- 部分的に変更された状態が残るか
- 再試行可能か
- 呼び出し元が行うべき後始末

C++例外を送出する関数は、例外型と送出条件を`@throws`へ記載する。
例外を送出しない境界関数では、`noexcept`を検討する。

### 8.8 定数、変数、型、メンバー

グローバル変数、ファイルスコープ変数、意味を持つ定数には`// ...`のコメントを付与する。
構造体・共用体・クラスのフィールドと列挙値には、Doxygenが各要素の説明として記録できるよう、
宣言直前に`/// ...`を付与する。コメントには、必要に応じて単位、範囲、初期値、所有権、
更新主体、排他方法を含める。

```cpp
// 応答待ちタイムアウト（ms）。設定範囲は100～60000
constexpr std::uint32_t RESPONSE_TIMEOUT_MS = 3'000U ;

// ドライバハンドル。initializeDeviceで取得し、finalizeDeviceで解放する
static HANDLE driverHandle = INVALID_HANDLE_VALUE ;

/**
 * @brief デバイスの動作状態を表します。
 * @note 制御スレッドだけが更新します。
 */
enum class DeviceState {
	/// 停止中。
	STOPPED,

	/// 入出力を実行中。
	RUNNING,

	/// デバイス応答待ち。
	WAITING_REPLY,

	/// 復旧操作が必要な異常状態。
	FAULT
} ;
```

構造体では、どのメンバーをどの実行主体が更新するかを明記する。
`///`は対応するフィールドの直前へ置き、空行や別の宣言を挟まない。
型と識別子は、同じ構造体内の論理グループでタブによりそろえてよい。

```c
/**
 * @brief サンプリングリングバッファの管理情報を保持します。
 */
typedef struct SamplingInfo {
	/// ISRだけが更新する書き込み位置。
	uint32_t	writeIndex ;

	/// 読み出しスレッドだけが更新する読み込み位置。
	uint32_t	readIndex ;

	/// 所有バッファ。samplingInfoFinalizeで解放する。
	uint8_t		*buffer ;

	/// bufferの確保容量（byte）。
	size_t		capacityBytes ;
} SamplingInfo ;
```

フィールドの説明が一行に収まらない場合も、宣言直前で`///`を各行に繰り返す。

```c
/// ISRだけが更新する書き込み位置です。
/// readIndexと一致した場合は、バッファが空であることを表します。
uint32_t	writeIndex ;
```

### 8.9 処理ブロックコメント

意味のまとまりごとに、そのブロックが達成する目的を直前へ記載する。

```cpp
// ドライバへ渡す前にJava配列をネイティブバッファへ固定する
jbyte *data = env->GetByteArrayElements( source, &isCopy) ;
```

コメントと対象処理の間に、無関係な宣言や別処理を挟まない。

### 8.10 if、else if、else

すべての`if`および`else if`の直前に、条件と成立時の処理意図が分かるコメントを付与する。
単なる式の読み替えではなく、業務状態または安全上の意味を書く。

```cpp
// デバイスハンドルを取得できていない場合はI/O要求を送信しない
if( driverHandle == INVALID_HANDLE_VALUE) {
	return false ;
}
```

複雑な制御条件では、`if(状態): 意図`形式を使用してよい。

```cpp
// if(応答待ち中かつ期限超過): 再送予約へ戻して次周期で要求を送信する
if(( state == DeviceState::WAITING_REPLY) &&
   (elapsedTimeMs >= responseTimeoutMs)) {
	state = DeviceState::SEND_PENDING ;
}
```

`else`の意味が自明でない場合は、分岐直前にコメントを付与する。

```cpp
// 自動設定の場合は論理プロセッサ数からスレッド数を決定する
if( mode == ThreadMode::AUTO) {
	threadCount = processorCount / 2U ;
}
// 固定設定の場合は指定されたスレッド数を使用する
else {
	threadCount = configuredThreadCount ;
}
```

### 8.11 for、while、do-while

すべてのループの直前に、反復対象、処理目的、終了条件が分かるコメントを付与する。

```cpp
// 登録済みデバイスを順次停止し、全ハンドルを解放する
for( Device &device : devices) {
	device.stop() ;
}
```

```cpp
// 終了要求を受けるまでデバイスイベントの受信を継続する
while( isRunning) {
	waitForDeviceEvent() ;
}
```

無限ループでは、終了または脱出させる主体と条件を必ず記載する。

### 8.12 switch

`switch`の目的と各`case`の業務上の意味を記載する。`break`と次の`case`の間は
1行空ける。

```cpp
// デバイス状態に応じて次の制御処理を選択する
switch( state) {
	// 送信予約中はデバイスへ要求を送信する
	case DeviceState::SEND_PENDING:
		sendRequest() ;
		break ;

	// 応答待ち中はタイムアウトを監視する
	case DeviceState::WAITING_REPLY:
		checkResponseTimeout() ;
		break ;

	// 停止中と異常中は周期処理を行わない
	default:
		break ;
}
```

意図的なfall-throughは、属性またはコメントで明示し、次の`case`へ進む理由を書く。

### 8.13 リソース取得と後始末

メモリ、ハンドル、サービス、ソケット、ロック、JNI配列、マッピングなどを取得する箇所では、
解放責任と異常経路をコメントまたは関数契約へ記載する。

C++ではRAIIを優先する。Cでは、単一の`cleanup`節を使う場合、どのリソースが
取得済みかを判別できるよう初期値を設定する。

```c
/**
 * @brief 設定ファイルを読み込みます。
 * @note fileとbufferは本関数内で取得し、成功・失敗にかかわらず本関数内で解放します。
 */
bool loadConfig( const char *path)
{
	FILE *file = NULL ;
	char *buffer = NULL ;
	bool result = false ;

	/* ... */

cleanup:
	// 確保済みバッファだけを解放する
	free( buffer) ;

	// オープン済みファイルだけをクローズする
	if( file != NULL) {
		fclose( file) ;
	}

	return result ;
}
```

`goto cleanup`は、Cで複数リソースの異常時後始末を一元化する用途に限定する。

### 8.14 排他、非同期、割り込み

ロック、アトミック変数、スレッド、コールバック、割り込みを扱う関数では、
次の事項を関数コメントまたは共有データのコメントへ記載する。

- 呼び出すスレッドまたは実行コンテキスト
- 同時呼び出しの可否
- 保持が必要なロックとロック順序
- コールバック先のスレッド
- 登録解除、停止、キャンセルを行う主体
- タイムアウト時と終了時の後始末
- 割り込み処理と通常処理の間で共有するデータ

```cpp
/**
 * @brief 受信キューへイベントを登録します。
 * @param[in] event 登録するイベント。
 * @note 複数の受信スレッドから同時に呼び出せます。
 * @note queueMutexを内部で取得します。callbackMutex保持中に呼び出してはいけません。
 */
```

### 8.15 JNI境界のコメント

JNI関数では、通常の関数契約に加えて次を記載する。

- 対応するJavaクラスとnativeメソッド
- JNI名が生成宣言により固定されること
- `jstring`、配列の文字コードまたは要素型
- ローカル参照、グローバル参照の所有権と寿命
- `Get*Elements`と`Release*Elements`の対応、解放モード
- Java例外を送出する条件と、送出後にネイティブ処理を継続するか
- ネイティブスレッドをJVMへattach/detachする主体
- `JNIEnv *`を別スレッドや次回呼び出しまで保持しないこと

```cpp
//------------------------------------------------------------------------------
/**
 * @brief Java側のRtScan.initからドライバを初期化します。
 *
 * @param[in] env 呼び出しスレッドに属するJNI環境。保持禁止。
 * @param[in] self 呼び出し元オブジェクト。本関数の終了後は参照しません。
 * @param[in] driverPath CP932のドライバパスを格納したbyte配列。NULL不可。
 * @return 初期化結果。JNI_TRUEは成功、JNI_FALSEは失敗。
 * @throws java.lang.IllegalArgumentException driverPathが不正な場合。
 * @post 取得した配列要素は全終了経路でReleaseByteArrayElementsにより解放します。
 */
//------------------------------------------------------------------------------
JNIEXPORT jboolean JNICALL Java_example_RtScan_init(
		JNIEnv *env, jobject self, jbyteArray driverPath) ;
```

JNIが生成したヘッダは直接編集せず、Java宣言を変更して再生成する。

### 8.16 Windowsドライバのコメント

カーネルモード関数では、通常の関数契約に加えて次を記載する。

- IRPのmajor/minor functionと、完了または下位ドライバへ渡す責任
- 呼び出し可能なIRQL、pageableかどうか
- `METHOD_BUFFERED`等のバッファ方式と、入力長・出力長の検証
- スピンロック、DPC、ISR、ワークアイテムとの関係
- デバイス拡張、MDL、物理メモリマッピングの所有権
- `NTSTATUS`と`IoStatus.Information`の設定条件
- PnP、power、unload時のリソース解放順序

```cpp
/**
 * @brief IOCTL_SCAN_START要求を処理します。
 * @param[in] deviceObject 対象デバイス。NULL不可。
 * @param[in,out] irp 完了対象のIRP。NULL不可。本関数が必ず完了します。
 * @return IRPへ設定した完了ステータス。
 * @pre PASSIVE_LEVELで呼び出すこと。
 * @warning 入力長がsizeof(ScanStartInput)未満の場合はバッファを参照しません。
 */
```

### 8.17 プリプロセッサとプラットフォーム依存処理

`#if`、`#ifdef`には、定義名の読み替えではなく、その構成を選択する理由を記載する。
長い条件ブロックの`#endif`には対応する条件を行末コメントで記載する。

```cpp
// 64bitビルドではポインタ幅に対応したIOCTL構造体を使用する
#if defined(_WIN64)
using IoctlAddress = std::uint64_t ;
#else
using IoctlAddress = std::uint32_t ;
#endif  // defined(_WIN64)
```

警告抑止は最小範囲とし、抑止理由、安全である根拠、可能なら管理番号を記載する。
ファイル全体やプロジェクト全体での無条件な警告抑止は行わない。

### 8.18 行末コメント

通常の処理意図は、処理前の独立したコメント行へ記載する。行末コメントは、
引数の対応、レジスタbit、固定フォーマットなど、複数行を
縦に比較する場合に限定する。行末コメントの開始位置は、同じ論理グループ内で
タブによりそろえる。構造体・共用体・クラスのフィールドと列挙値には行末の`//`を使わず、
8.1および8.8に従って宣言直前の`///`を使用する。

```cpp
request.run = false ;		// bit 0: 運転指令OFF
request.reset = true ;		// bit 1: 異常リセットON
request.reserve = false ;	// bit 2: 予約領域は常にOFF
```

値の意味は「ON/OFF」だけでなく、外部仕様上の役割が分かるようにする。

### 8.19 TODOと禁止事項

TODOを残す場合は、管理番号と完了条件を記載する。

```cpp
// TODO(PROJ-1234): 新ドライバ移行後にWindows 7互換分岐を削除する
```

次を禁止する。

- コードと矛盾するコメントを残す。
- 不要になったコードをコメントアウトしたまま残す。
- コードの日本語訳だけで、理由や契約を説明しない。
- 作業者しか理解できない略語を説明なしで使用する。
- 「暫定」「とりあえず」「たぶん」だけで理由を記録する。
- 管理番号または完了条件のないTODOを残す。
- デバッグ用の`printf`やテストコードをコメントアウトして保存する。
- 誤った呼出形式をコメントへ複製する。
- ログ出力だけで処理仕様を説明したことにする。
- 区切り線や空白だけでファイルを過度に装飾する。

## 9. ヘッダと公開API

### 9.1 宣言の最小化

ヘッダには利用者が必要な宣言だけを公開する。実装専用の定数、型、関数、
変数は実装ファイルへ置き、Cでは`static`、C++では無名名前空間等で内部リンケージにする。

ヘッダでグローバル変数を定義しない。必要な場合も`extern`宣言と単一定義を分離し、
共有状態、初期化順序、排他方法をコメントする。

### 9.2 C互換API

C++ヘッダからC ABIを公開する場合は、次の形式を使用する。

```cpp
#ifdef __cplusplus
extern "C" {
#endif

bool device_initialize( const DeviceConfig *config) ;

#ifdef __cplusplus
}
#endif
```

DLL公開マクロ、呼出規約、構造体のパッキング、整数幅はABIの一部として管理する。
公開済みの構造体へ安易にメンバーを追加せず、サイズまたは版数フィールドを検討する。

### 9.3 include規則

- 未使用、重複した`#include`を追加しない。
- 実装が直接利用する型・関数のヘッダを直接インクルードする。
- ワイルドカードや絶対パスでインクルードしない。
- 大文字・小文字を実ファイル名と一致させる。
- Windowsのマクロ汚染が問題になる場合は、ビルド設定で`NOMINMAX`等を統一する。
- ヘッダ内で`using namespace`を使用しない。

## 10. 型、定数、列挙、マクロ

### 10.1 整数型

外部データ、ファイル、通信、IOCTL、ABIでは、幅が明確な`stdint.h`または`<cstdint>`の
整数型を使用する。バッファサイズと要素数には`size_t`または`std::size_t`を使用する。

Windows API境界では`DWORD`、`ULONG`等の要求型を使用してよいが、内部型との変換時に
範囲と符号を確認する。ポインタを`DWORD`や`int`へ格納しない。

### 10.2 boolean

- Cでは`stdbool.h`の`bool`を内部処理に使用する。
- C++では`bool`を使用する。
- Windows API境界では`BOOL`、JNI境界では`jboolean`を使用する。
- 異なるboolean型の変換は、`TRUE/FALSE`と`JNI_TRUE/JNI_FALSE`を明示する。

### 10.3 定数

数値や文字列に業務上の意味がある場合は、名前付き定数とする。単位、bit位置、
範囲を名称またはコメントで示す。

C++では`constexpr`、型付き`enum class`を優先する。Cでは型付きの`const`、`enum`、
必要最小限のマクロを使用する。

```cpp
constexpr std::uint32_t MAC_ADDRESS_SIZE_BYTES = 6U ;
constexpr std::uint32_t CONTROL_REQUEST_BIT = 0x01U ;
```

### 10.4 マクロ

マクロは、条件コンパイル、C互換の属性、コンパイル時定義など必要な場合に限定する。
関数形式マクロより、C++では`constexpr`関数、Cでは`static inline`関数を優先する。

関数形式マクロでは、引数と式全体を丸かっこで囲み、引数を複数回評価しない。
マクロの副作用、使用条件、結果型をコメントする。

## 11. 変数、ポインタ、メモリ、リソース

### 11.1 変数のスコープと初期化

変数は使用する最小スコープで宣言し、宣言時に初期化する。未初期化の出力値や
ハンドルを残さない。

```cpp
HANDLE deviceHandle = INVALID_HANDLE_VALUE ;
std::uint32_t bytesReturned = 0U ;
bool isCopy = false ;
```

複数変数を1宣言へ詰め込まない。ポインタと非ポインタを同じ宣言へ混在させない。

### 11.2 NULL

Cでは`NULL`、C++11以上では`nullptr`を使用する。整数の`0`をNULLポインタとして
使用しない。Windows APIが返す`INVALID_HANDLE_VALUE`と`NULL`を混同しない。

入力ポインタは使用前に検証する。ただし、NULL不可が型や契約で保証され、
性能またはカーネル要件により重複確認しない場合は、その前提を`@pre`へ記載する。

### 11.3 配列とバッファ

配列またはバッファのポインタには、原則として長さまたは容量を同時に渡す。
コピー、書式化、変換の前に、終端文字を含む必要量を確認する。

`sprintf`、`strcpy`等の境界を指定できない関数は新規コードで使用しない。
標準ライブラリ、`snprintf`、安全なラッパーなど、対象処理系で長さを検証できる方法を使う。

### 11.4 所有権

所有権は型と関数コメントで明確にする。

- C++では自動変数、標準コンテナ、スマートポインタ、専用RAII型を優先する。
- `std::unique_ptr`は単独所有、`std::shared_ptr`は共有所有が必要な場合だけ使用する。
- 借用ポインタを所有ポインタとして解放しない。
- Cでは、生成・解放関数を対にし、どちらが解放するかをAPIコメントへ記載する。
- Windowsハンドルには、対応する`CloseHandle`、`FreeLibrary`、`CloseServiceHandle`等を確認する。

## 12. 制御構文と式

### 12.1 条件式

条件式は肯定形で読みやすくし、複雑な否定の組み合わせを避ける。代入と比較を
同じ式に混在させない。複合条件は丸かっこと改行でAND/ORの関係を明確にする。

booleanを`true`、`false`と比較しない。整数やハンドルをbooleanとして暗黙評価する場合は、
ゼロ、NULL、無効値のどれを判定しているかが明確な式にする。

### 12.2 早期return

入力不正や処理対象外は、早期`return`で正常経路のネストを浅くしてよい。
ただし、取得済みリソースを解放せずに戻らない。C++ではRAII、Cでは`cleanup`節等で保証する。

### 12.3 switchのdefault

`switch`には原則として`default`を記載する。すべての列挙値を明示し、将来の追加を
コンパイラ警告で検出したい場合は省略してよいが、その方針をコメントする。

### 12.4 符号、桁あふれ、キャスト

符号付き・符号なし整数の比較、切り詰め、乗算後のサイズ計算、ポインタ幅の変換を
暗黙に行わない。キャストの前に値域を検証する。

C++ではC形式キャストを新規に使用せず、`static_cast`、`reinterpret_cast`等で意図を示す。
Cでは、不要なキャストで型不一致の警告を隠さない。

## 13. 関数設計

### 13.1 単一責務

関数は、名前で説明できる1つの責務を持つ。初期化、I/O、変換、ログ、後始末が
過度に混在する場合は、失敗単位とテスト単位に分割する。

### 13.2 引数と戻り値

- 入力は可能な限り`const`にする。
- 出力引数より戻り値を優先する。ただしC API、複数出力、Windows API規約では出力引数を使用してよい。
- 出力引数は名前と`@param[out]`で明示する。
- boolean引数が呼び出し箇所で意味不明になる場合は、列挙型または設定構造体を使用する。
- 大きなC++オブジェクトは、所有権を移さない限り`const`参照で渡す。

### 13.3 副作用

グローバル状態、OS設定、デバイス、ファイル、レジストリ、Java例外状態を変更する関数は、
その副作用と復元方法を関数コメントへ記載する。

### 13.4 再入可能性とスレッド安全性

公開APIは、再入可能か、複数スレッドから呼び出せるかを記載する。
スレッド安全でない場合は、呼び出し元が保持すべきロックまたは呼出順を示す。

## 14. C++固有規則

### 14.1 RAII

メモリ、ハンドル、ロック等は、原則としてオブジェクトの寿命へ結び付ける。
デストラクタは例外を送出しない。所有リソースを持つクラスは、コピー、ムーブ、
代入、破棄の方針を明確にする。

### 14.2 クラス

- クラスは不変条件と責務を`@brief`または詳細説明へ記載する。
- メンバーは原則として`private`にする。
- コンストラクタで完全に初期化する。
- 暗黙変換を意図しない1引数コンストラクタには`explicit`を付ける。
- オーバーライドには`override`を付ける。
- 継承を想定しないクラスには`final`を検討する。
- `const`メソッド、`noexcept`を契約に合わせて使用する。

### 14.3 名前空間

ライブラリコードはプロジェクト固有の名前空間へ入れる。ヘッダ内で
`using namespace`を使用しない。名前空間の終端には、長い場合だけ名称をコメントする。

### 14.4 例外

プロジェクト単位で例外の使用可否を決める。JNI、C ABI、Windowsコールバック、
カーネルモード等の境界をC++例外が越えないよう、境界内でエラーへ変換する。
例外禁止環境では、戻り値と出力状態の規則を統一する。

## 15. エラー処理、ログ、セキュリティ

### 15.1 エラー処理

APIの戻り値を確認し、失敗後に無効な値を使用しない。エラーを無視できる場合は、
無視して安全な理由をコメントする。呼び出し元へ失敗を返す前に、取得済みリソースと
部分状態を整理する。

`GetLastError()`等は、後続APIによって上書きされる前に保存する。

### 15.2 ログ

ログには、操作、対象、結果、診断に必要なエラーコードを含める。パスワード、秘密鍵、
トークン、個人情報、不要なバッファ内容を出力しない。

```cpp
const DWORD errorCode = GetLastError() ;
logError( "CreateFile failed", devicePath, errorCode) ;
```

本番コードで`printf`だけに依存しない。ログレベル、出力先、文字コードを
プロジェクトで統一する。

### 15.3 入力検証

外部境界では、ポインタ、長さ、範囲、列挙値、文字列終端、パス、IOCTLサイズを
使用前に検証する。特にサイズ計算は、加算・乗算の桁あふれを確認してから確保する。

### 15.4 警告と静的解析

新規コードはコンパイラ警告を残さない。可能なプロジェクトでは警告をエラーとして扱う。
警告抑止は、対象箇所、理由、安全根拠を明記して最小範囲へ限定する。
スタック保護、Control Flow Guard等、ツールチェーンが提供するセキュリティ保護を
理由なく無効化しない。旧SDKやドライバ要件により無効化する場合は、対象、理由、
代替対策をビルド設定のコメントへ記載する。

## 16. JNI・Windows・ドライバ境界の実装規則

### 16.1 JNI

- `JNIEnv *`をグローバル変数へ保存しない。
- `GetString*`、`Get*ArrayElements`の結果をNULL確認し、対応するReleaseを全経路で実行する。
- Java例外が保留中の場合に、許可されていないJNI関数を続けて呼び出さない。
- グローバル参照は`NewGlobalRef`で作成し、責任箇所で`DeleteGlobalRef`する。
- ネイティブスレッドは、使用前にattachし、責任を持ってdetachする。
- Javaの`byte[]`を文字列として使う場合は、文字コードとNULL終端の有無を契約化する。
- `jlong`とポインタを相互変換する場合は、`intptr_t`等を介して幅を保証する。

### 16.2 Windowsユーザーモード

- `HANDLE`の無効値が`NULL`か`INVALID_HANDLE_VALUE`かをAPIごとに確認する。
- 取得APIと対応する解放APIを一致させる。
- ANSI版とUnicode版のAPIを暗黙に混在させず、プロジェクト方針を決める。
- `GetLastError()`を返すAPIと、返さないAPIを区別する。
- x86とx64でサイズが変わる型をファイル形式やIOCTLへ直接保存しない。

### 16.3 Windowsドライバ

- ユーザー入力を信頼せず、IRPバッファ長とアクセス方法を検証する。
- IRQLに適さないAPI、ページ可能メモリ、待機処理を呼び出さない。
- IRPを完了する主体を1つにし、二重完了を防ぐ。
- 共有状態には、実行コンテキストに適した同期手段を使用する。
- PnP、power、unloadの各経路で、割り込み、マッピング、シンボリックリンク、デバイスを逆順に解放する。
- 物理アドレスとポインタの変換では、32bitへの切り詰めを行わない。

## 19. 修正時の進め方

不具合修正または仕様追加では、コードを書く前に次を定義する。

1. 不具合を再現できる最小ケース、または仕様を確認できる最小ケース
2. 入力条件と前提環境（OS、x86/x64、JVM、ドライバ状態、IRQL等）
3. 期待結果と失敗時の状態
4. 確認対象のファイル、関数、API境界
5. 自動テスト、静的解析、またはソース単位の確認手順
6. リソースリーク、範囲外アクセス、競合を確認する方法

実装は定義した確認を通すための最小範囲とする。同じ分類の不具合を繰り返している場合は、
再発防止チェックを先に追加する。

環境依存で自動実行できない場合も、入力条件、期待結果、確認対象関数を明記し、
未実施項目と理由を記録する。

## 23. DriverCrateの整形・検査との適用関係

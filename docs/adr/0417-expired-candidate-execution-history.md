# ADR 0417: 失効候補の検証表示と所有する実行履歴の分離

- 日付: 2026-10-27
- 状態: 採用（実装前決定。source・内部試験・実機導入受入は別に記録する）
- 関連: ADR 0150、0416、G13-I7r264b1/t1

承認済み二NIC初回導入の有限実試験562は一件適用・一件未適用だった。通常画面は導入後に
全candidateのinstallableをfalseへ失効させる。その初回候補はREADY assessmentとの整合を
isCandidateDetailsValidに拒否され、詳細整形が個別実行結果の追記前に戻っていた。
原個別HRESULTが読めないUI不具合は確定したが、第二の導入失敗の原因は未確定である。

## 比較と決定

候補の検証根拠を不変にしてsession選択可否を別管理する案は、全選択経路の変更を伴う。
今回は既存の失効・検証契約を維持し、検証本文と実行履歴の表示だけを分ける最小案を採用する。

1. isCandidateDetailsValidとinstallable=false、controllerのsession失効、選択・実行guardを変更しない。
   検証に矛盾があれば従来の結合拒否を表示し、その候補を検証済み・実行可能に見せない。
2. UIが所有する候補要素そのものに結び付いた個別実行結果だけは、検証本文を拒否した場合も
   読取り専用の過去履歴として表示する。外部copy・同名・同版・同deviceの別候補からは参照しない。
   既存の候補順とidentity照合による結果保存、新scan開始/受理時の破棄を維持する。
3. 履歴は現在の適用性・検証成功・導入許可・現在版を意味しないと明示する。
   個別の取得/導入診断と必要構成の各段階を保持し、成功・失敗・未実行・反映待ちを混同しない。
4. Provider/backend、署名・hash・適用性・EULA・復旧と実導入経路は変更しない。
   旧稼働アプリの結果復元や第二の失敗原因解明、実導入の再試行は今回の範囲に含めない。

## 有限回帰と取消し

既存U21の真署名索引から発行した異なるdeviceの二INITIAL_INSTALL候補を、実workerの
部分結果とcontrollerのsession0へ通し、実詳細dialogで各履歴を読む。役割別結果の固定表示入力も
同じ所有二候補で別に確認する。偽copy・別candidate/device・結果なし・不正assessmentの検証拒否、
新scan reset、checkbox/Space/詳細選択/導入commandの拒否とProvider再実行なしを確認する。
修正前の再現失敗と修正後のDebug/Release・既存unit/UI・変更品質gateを別に保存する。
取消す場合は表示変更だけを戻し、実driver状態や旧記録へ変更を加えない。

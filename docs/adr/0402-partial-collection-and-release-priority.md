# ADR 0402: 部分収集を保持し公開準備を先行する

- 日付: 2026-10-25
- 状態: 採用。ADR0397の週次残存期間条件と工程優先順位を更新する。

## 判断

利用者の「ひとまず取得できない所は後回し」「現実的には一週間に一回成功すればいい」
「実際に運用しログがあれば後日切り分け可能」「先に公開可能なレベルが優先」を採用する。
登録済み対象の日次試行を維持し、週内に一回程度の成功を運用目標とする。
全取得先の同時fresh成功や七日間の実運用を、最終sourceと配布物を確定する前提にしない。
失敗・HOLD・未評価を元の分母と理由へ残し、未知や過去の成功を現在の成功へ換算しない。
新製品拡大は先行しない。

週次は運用目標であり、公開時に必ず七日超の有効期間を残す条件ではない。
prepare/sign/publishの共通検査を、実現在UTCで原recordとmanifestが有効である条件へ揃える。
全原recordのhashと期限min、manifestの発行時刻 <= 実現在 < 期限minを検査し、
新規署名前・公開前・CAS直前も再検査する。残存七日以下の束もその原期限内だけ扱える。
期限到達時は拒否し、時計が確認不能な場合や発行時刻より前の場合も拒否する。
短いrecordを任意に除外して公開を成功扱いせず、期限や原byteを変更しない。
旧週次専用関数・診断・条件flagの互換分岐は残さない。

## 既存処理を維持する範囲

- 成功Aと失敗/HOLDのBは別に記録し、Aだけを候補へ接続する。
  新成功Bを追加する場合、未失効の前回成功Aは原recordと原期限を保持する。
  assemblyが原期限切れの候補を外す場合は、既存の除外理由をbuild-reportへ残す。
- 全失敗・全HOLD・空成功のrunでは、前回headやassetを空の新世代へ置き換えない。
  旧公開成功は原byte/署名/期限のまま保持する。期限切れの保存と現在利用の許可を分ける。
- 新recordの発行は、既存の同runの私有typed観測、24h未満のfresh窓、内容/PAGE/独立根拠の
  各原時刻からの八日上限を維持する。保存済み成功の保持を、新発行用のfresh根拠に変換しない。
  新しい発行時刻や同hashの再取得だけで、手動確認時刻・期限・権限を更新しない。
- 索引署名・原hash/実取得byte・INF/CAT/参照本体・端末適用性・同意/復旧・世代下限を維持する。
  EXEコード署名の延期を索引署名の省略へ広げない。HTTP待機/Retry-After・予算・課金・
  同じroot/所有者/namespaceを保持し、resetや別counterで迂回しない。
- 通常日次は未署名候補まで、署名と公開は明示手動のままとする。
  実driver導入とpush/tag/Release等の実公開は、それぞれ別の具体的明示指示を必要とする。

## 今後の新対象の共通保守規則

利用者の追加指示により、今後の新device・メーカー・製品にも同じ部分収集規則を適用する。
台帳登録、実取得、内容検査、端末適用性、導入の各実績を分け、取得/検査未確認の登録を
利用可能driver数へ数えない。取得不可・一時障害・HOLDは理由と最終試行・次回試行下限を
既存の保護run/result/待機履歴へ残し、次回の許可済み試行または必要な手動reviewへ送る。
他対象の処理と公開準備は継続し、新対象の全成功や全機器網羅を公開要件にしない。
日次試行・週内一回程度の成功は目標であり、成功保証・実期限延長・HOLDの自動解除ではない。

通常の対象追加は手動調査と外部JSON台帳/locator/profileの保守で行う。
メーカー固有のアプリ分岐や製品AI、自動調査を追加しない。共通処理が扱えない新形式だけ
parser実装と実測を別工程へ登録する。今回はこの共通規則の明文化までとし、新対象を追加しない。

## 診断の再利用

新しいログ基盤は作らない。既存のrun/plan/build-reportが全target・成功/失敗/HOLDの理由・
件数を持ち、原native result/candidateがPAGE/PAYLOADの完了段階・HTTP status・
全体と個別INFのresult/NativeError数値を保持する。
requestのattemptedAt/endedAtとreservation/nextDueAtから、実試行の開始/終了・秒単位の
経過時間・次回試行下限を追える。runのstartedAtとmetadata reportのstartedAt/finishedAtも
既存保存を使う。未試行・中断や全runの精密なwall durationを推測で補完しない。
元失敗とlastSuccessを別に保持し、後日切り分ける根拠とする。

本文・URL等を含む保護されたprivate診断と、件数/状態/診断codeの一般summaryを区別する。
credential・生inventory・URL/tokenを一般ログへ追加せず、private run/result/bodyや秘密鍵を
公開assetへ入れない。ログを使う方針はprivacy境界を撤回するものではない。

## 有限受入

実network/鍵/Task/署名/実導入/remote writeを使わないfakeで次を固定する。

1. 成功A+失敗/HOLDBでもAを候補へ接続し、失敗/HOLDを分母と理由へ残す。
2. 未失効の旧A+新成功Bで原record/期限を保持し、全失敗時は旧head/assetを保持する。
3. 原期限切れは理由付きで除外または拒否し、期限を延長しない。
4. 残存七日以下のprepare/sign/publishと短期間束を受理し、expiry到達を拒否する。
   prepare後・署名後・CAS前の時間経過でも、原byte/署名束/世代下限を変更しない。
5. 既存の発行fresh窓・現在時計拒否と、保存済み旧成功の原期限を別々に確認する。
6. 既存の保存診断が件数・失敗理由/段階・数値結果・開始/終了/次回下限へ結び付くことを確認する。

変更Pythonと関連回帰、syntax、公開source closureと文書一致を有限確認する。
C++を変更しない本差分で、既に受入済みの全C++build/全unit/全保持監査は反復しない。
最終公開snapshot/配布物は後段で一回再結合し、変更前byteの資格を自動継承しない。
新しい有効な署名索引と通常アプリのPublic正例、実Task運用/長期観測/別PC/実導入が
未確認である事実を維持し、方針採用だけを実成功と表現しない。

## 2026-10-26: 手動発行入口の片系統接続

ADR0403により、同じprepare/sign/publishで汎用のみ/nativeのみ/両方の成功入力を
明示pinして進められる契約へ揃える。未指定両方・不完全対・指定入力の不適合を拒否し、
疑似headやauthorityを合成しない。原内容証拠と全経路必須のLEGACY_FENCEを分け、
既存claim履歴の世代・署名/CAS不確定意図、原期限/待機を保持する。
有限fakeの成功をfresh実取得や新しい有効Public索引へ換算せず、実公開の別承認を維持する。

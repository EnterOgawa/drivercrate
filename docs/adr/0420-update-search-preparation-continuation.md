# ADR 0420: 通常検索から同意付き取得・検査へ続く

- 日付: 2026-10-28
- 状態: 検索後の自動確認はADR0422で置換。G13-I7r269b/cの実装・内部検証は履歴として保持する。
- 関連: ADR 0144、0416、0419、G13-I7r269

## 背景

通常の「更新を検索」は再検出・現在device列挙・Provider検索を終えても、取得計画を案内するだけで
停止していた。未導入deviceに索引metadataが届いても、利用者が別の「取得準備」を操作しない限り
内容・端末適用性の検査と導入候補発行へ進まない。検査前にcheckboxがないこと自体は正しいが、
検索操作だけでは選択可能な候補へ到達しない製品導線を修正する。

## 決定

以下はG13-I7r269で採用した旧決定の履歴である。現行の通常導線はADR0422へ置き換え、
検索後に自動取得確認を開かない。旧方針の内部合格を新byteの実UI受入へ継承しない。

1. UIから明示開始した通常STANDARD検索は、成功終端で有効かつ未使用の取得計画を受理した場合、
   一覧反映後に既存の取得確認へ一回だけ続く。既に導入可能な候補が混在しても続く。
   検索開始時に公式探索をmetadata限定へ明示した場合、専用METADATA_ONLY検索、内部再監査、
   導入後の限定現在観測からは続けない。
2. UI所有の有限な継続snapshotを元scan operation/session/planへ結合し、posted messageで開始する。
   受信時にも現在state、operation、session、未使用planと終了/確認中でないことを照合する。
   継続は確認前に消費し、新検索、取消し、拒否、失敗、手動の取得準備、終了後に自動再試行しない。
   旧通知や二重通知で新しい計画を開始しない。
3. 既存の全体/対象確認、必須EULA全文・revision、必要条件、回線許可と最終件数確認を保持する。
   承認された対象だけ既存worker queueで有限予算の取得・署名索引/原hash/INF閉包/Windows rank/
   適用性/proof検査へ送る。UI threadへ同期network処理を追加せず、検査前情報を導入許可へ変えない。
   取消し・規約拒否・取得/内容失敗の理由と検査済みの独立候補を保持する。
4. 検査後に一deviceの導入可能候補が一つなら、既存のdevice行checkboxがその一候補を明示選択する。
   複数候補は勝手に選ばず、通常詳細で一候補を指定する既存導線を保つ。推奨filterは検査済みの
   初回導入候補も表示・明示選択できるようにする。初回候補は初期選択・推奨一括選択へ加えない。
5. 導入同意、復旧、stale拒否、導入後の限定観測・結果保持は変更しない。新button、設定、Provider、
   汎用workflow基盤を追加しない。取得準備buttonは再確認・取消し・結果閲覧として維持する。

## 検証と限界

既存fake constructorと低位HTTP/Windows表を使い、通常検索→確認/EULA→取得・内容検査→
通常checkboxを同じUI経路で確認する。二device、ready/未取得の混在、唯一/複数候補、取消し、
規約拒否、失敗、旧通知、新検索、close、再入を有限に回帰する。実network、OS再検出、実導入を
内部試験から呼ばない。新byteの通常実機受入は主担当review後の別工程とし、内部成功を継承しない。

## 戻し方

UI継続と初回filterの変更を元に戻せば、従来の明示「取得準備」経路へ戻せる。
保護store形式、索引署名、取得・導入権限、package/receiptを変更しない。
